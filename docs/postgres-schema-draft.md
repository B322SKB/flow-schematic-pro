# PostgreSQL schema draft — P&ID PoC

Status: design draft, not yet applied to a database. The first backend increment should validate this model against the existing TypeScript `Scheme` type before creating migrations.

## Design constraints

- PostgreSQL is the authoritative store once server persistence is introduced.
- UUIDs are generated by the application and remain stable across CAD geometry edits.
- A project can contain one or more drawings; the current browser model initially maps one existing `Scheme` to one drawing.
- A drawing revision is immutable. Calculations and MTO outputs reference the exact revision used.
- Accepted operations are append-only and receive a monotonically increasing revision number per drawing.
- JSONB snapshots preserve the full engineering model while the PoC stabilizes its normalized entity schema. Do not duplicate every engineering property into columns prematurely.

## Proposed tables

### Identity and access

- `app_users`: UUID, normalized unique email, display name, password hash, active flag, timestamps.
- `user_sessions`: UUID, user UUID, hashed opaque session token, expiry, revocation timestamp, created timestamp. Never store a raw session token.
- `projects`: UUID, name, description, created/updated timestamps, created-by user UUID.
- `project_memberships`: project UUID, user UUID, role (`owner`, `editor`, `viewer`), created timestamp. Unique project/user pair.

### Drawing and revision history

- `drawings`: UUID, project UUID, name, current revision number, timestamps.
- `drawing_revisions`: UUID, drawing UUID, revision number, parent revision number, complete immutable Scheme JSONB snapshot, SHA-256 checksum, author UUID, created timestamp. Unique drawing/revision pair.
- `drawing_operations`: UUID (idempotency key), drawing UUID, base revision, resulting revision, actor UUID, operation type, JSONB payload, timestamp. Unique drawing/resulting-revision pair and unique operation UUID.

The write transaction must:
1. lock the drawing row;
2. compare the submitted base revision with `current_revision_no`;
3. validate the operation against the current semantic snapshot and permissions;
4. write the operation and immutable next snapshot;
5. advance `current_revision_no`;
6. commit before broadcasting the accepted operation.

A stale base revision returns a conflict response; it must not be silently rebased or overwritten.

### Engineering outputs

- `calculation_runs`: UUID, drawing UUID, source revision number, solver version, input assumptions JSONB, result JSONB, warnings JSONB, status, author UUID, created timestamp.
- `mto_runs`: UUID, drawing UUID, source revision number, generator version, assumptions JSONB, result JSONB, author UUID, created timestamp.

Both outputs reference an immutable revision. Re-running a calculation creates a new record rather than changing an old result.

## Integrity requirements

- Foreign keys for all user, project, drawing and revision relationships.
- Unique normalized email.
- Unique `(project_id, user_id)` membership.
- Unique `(drawing_id, revision_no)` revision.
- Unique operation UUID for retry/idempotency.
- Unique `(drawing_id, resulting_revision_no)` accepted operation.
- Check constraints for valid membership roles and positive revision numbers.
- Indexes on project memberships by user, drawings by project, revisions by drawing/revision, operations by drawing/revision, and calculation/MTO runs by drawing/source revision.
- Password hashes use a modern password-hashing algorithm (Argon2id preferred); session tokens are random, high-entropy values stored only as hashes.

## Deliberately deferred

- Redis, distributed locks and event brokers.
- Fine-grained entity tables and full event sourcing.
- External identity providers / AD / LDAP.
- Multi-tenant organization hierarchy.
- CAD file binary storage in PostgreSQL; files belong in controlled file storage with metadata/checksums in the database.

## Validation gate before implementation

1. Map the existing `Scheme`, `PidNode` and `Pipe` types into the snapshot contract.
2. Confirm whether the first pilot needs multiple drawings per project or one-to-one mapping is sufficient.
3. Implement transactional revision allocation and stale-write rejection.
4. Test idempotent retries, concurrent writes, rollback on invalid operations, and recovery from process restart.
5. Only then connect the browser store to the API and add PostgreSQL to Docker Compose.
